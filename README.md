# ttoss skills

Agent skills shared across ttoss projects. The Flow skills are built on [Get Things Flowing](https://flow.ttoss.dev/docs/agents/protocol.md) (GTF), the method Flow defines for agents.

**Rule of thumb:** GTF is a general method, for anyone in any profession; the ttoss [Agentic Workflow](https://ttoss.dev/docs/engineering/workflow) is GTF applied to product development: a change goes through its gates, is integrated, released and verified, whatever the code host or the kind of delivery; these skills are how an agent runs it. A rule true of any work belongs in GTF, one true of software delivery in the Agentic Workflow, how an agent carries it out here, and one true of a single product in that project's parameters.

The [delivery process](https://github.com/ttoss/ttoss/blob/main/docs/website/docs/engineering/workflow/process.md) (seven stages, one owner each, and the transitions between them), the [parameters](https://github.com/ttoss/ttoss/blob/main/docs/website/docs/engineering/workflow/parameters.md) and the [routines](https://github.com/ttoss/ttoss/blob/main/docs/website/docs/engineering/workflow/routines.md) that fire the runs are the Agentic Workflow's own pages, which the skills read from ttoss/ttoss's default branch, so an edit to them belongs there. How a project integrates, releases and proves work done are its answers to the process's [parameters](https://github.com/ttoss/ttoss/blob/main/docs/website/docs/engineering/workflow/parameters.md), which `flow-setup` defines with the user. GTF always wins; where a project answers a parameter, its answer is followed; the skills supply a default for every parameter left empty. Each skill lives in `skills/<name>/SKILL.md`; install it with the [`skills` CLI](https://github.com/vercel-labs/skills) (`npx skills add ttoss/skills`), which records it in the consuming repo's `skills-lock.json`.

| Skill | What it does |
| --- | --- |
| [`flow`](skills/flow/SKILL.md) | Runs a project's Agentic Workflow from its Flow graph: one tick reads the graph, reviews and integrates by the project's merge rule, runs its release procedure and the checks that came due, and delegates ready tasks to child agent runs it records, then ends in one line. The project's routines fire the tick; a task id or `tag:<name>` focuses it on part of the graph, `--max-runs N` caps child runs and `--chase` sends each person what the graph waits on them for instead of a tick. |
| [`flow-setup`](skills/flow-setup/SKILL.md) | Sets a repository up for the Agentic Workflow, or audits it again: installs the skills, walks the user through the project's parameters (runtime, intake, ready brief, decisions, before proposing, review, merge rule, release procedure, closing evidence, delivery kinds) from what the repo already says, removes delivery rules that only restate GTF or the skills, writes the entry section every session reads, proposes the Flow standing decision and opens a PR for review; once it merges, creates the routines that fire the runs, and `routine <name>` adds a project's own. |
| [`flow-friction`](skills/flow-friction/SKILL.md) | Files friction met in a skill, the Get Things Flowing method or the Flow MCP tools as an issue here, deduplicated against open issues, and links it back to the Flow task. |
| [`token-audit`](skills/token-audit/SKILL.md) | Finds where a project's Claude Code sessions waste tokens, from measurements: the instruction corpus every session loads (`scripts/measure_instructions.py`), scoped rules stacking in busy packages, real session usage (cost, context growth, cache rewrites, PR wake-ups), each routine's model against its work, and tool payloads that bloat context. Ranks fixes by measured saving and changes nothing without the user's word; `--routine` runs it as a Flow project's weekly audit, filing each fix as an `incubated` task. |
