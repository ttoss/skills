# Loop rules

The rules the manager applies and every child follows, from [ttoss/ttoss#1336](https://github.com/ttoss/ttoss/issues/1336), battle-tested in naturali and soat. They extend [Get Things Flowing](https://flow.ttoss.dev/docs/agents/protocol.md) (GTF) and never restate it: each rule cites the GTF rules it applies and says only what the loop adds. Read the cited ids in the protocol; when GTF changes, the loop follows. Anything not covered here falls back to GTF. A project's own rules come after these and only fill what both leave open ([precedence](../../flow-setup/SKILL.md#precedence)).

| # | Loop rule | GTF it applies | What the loop adds |
| --- | --- | --- | --- |
| 1 | **Autonomy** | GTF-T1, GTF-T3, GTF-N6 | A clear task is worked to its close without the user. Undelegated choices include product intent, the project's human-reserved decisions and any open security, auth, billing, data-loss, migration or public-contract choice; each blocks only its task, other work continues. |
| 2 | **Open questions only** | GTF-T3 | A choice the task, the standing decision or a rule already makes is not open: implement it. An open one runs a Pareto / long-term gate (the `guardian` skill, when installed) before it becomes a `decision`. |
| 3 | **Standing decision as basis** | GTF-T1, GTF-A2, GTF-E4 | One standing decision per project authorises the loop; it is cited on every write. |
| 4 | **Done = works on the real API** | GTF-E3, GTF-E8, GTF-T4, GTF-T5 | The closing evidence is real calls against the production target. Each release gets a `Test <project> vX.Y.Z in production` task; a failure is a task that `blocks` the one it failed. |
| 5 | **Step order** | GTF-E1, GTF-T2 | First open step, no waiting: merge a done PR → cut the upstream release whose batch is ready → bump the downstream → work the tasks it unblocks → test the release in production and close what it shipped → start the next ready task, including while a deploy runs. |
| 6 | **Release batching** | GTF-N1 | One open `Release <upstream> (next)` task always exists; tasks meant to ship `block` it. Cut once ≥ 2 blockers merged and no other blocker is about to go green. When cutting: retitle the task with the version, create the next `Release (next)`, re-point open blockers at it, tell running children its id, and write `Bump <downstream> to vX.Y.Z` (blocked by the release) and its `Test … in production` (blocked by the bump). |
| 7 | **Every wait lives in Flow** | GTF-S3, GTF-S5, GTF-N4 | CI, a deploy or a pipeline is a `scheduled` wait; a reviewer is `external`. The PR is an `implements` reference and the next step is in the body. |
| 8 | **One manager, which implements nothing** | GTF-T6 | The manager merges, releases, starts and archives sessions; each ready task gets its own child session, which pursues it to its close. |
| 9 | **The manager holds no state** | GTF-S1, GTF-S4, GTF-E9 | A delegated task cites its child session URL as a `context` reference; a new manager rebuilds everything from `get-next`. |
| 10 | **Parallel; validation wins a slot** | GTF-E8, GTF-R6 | Advance every cleared wait before new work. Under the session limit (`--max-sessions`), a free slot goes to production validation first. |
| 11 | **Sessions close as they finish** | GTF-S3 | A session whose part is done and written back is archived by its spawner, or by itself when nothing spawned it. |
| 12 | **Branches** | — | A merged PR frees its branch: restart it from the default branch for the next task. |
| 13 | **Bugs and findings** | GTF-T4, GTF-C1, GTF-C3, GTF-A3 | Work the task cannot finish without becomes a task that `blocks` it, with the evidence (`file:line`, request, log). Everything else is captured at once, without asking (search first, add to a match), and the user is told when it is urgent. |
