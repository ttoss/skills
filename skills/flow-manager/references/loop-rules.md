# Loop rules

The rules the manager applies; children get only what they need through the [child prompt](child-prompt.md). They extend [Get Things Flowing](https://flow.ttoss.dev/docs/agents/protocol.md) (GTF) and never restate it: each rule cites the GTF rules it applies and says only what the loop adds. Read the cited ids in the protocol; when GTF changes, the loop follows. Anything not covered here falls back to GTF.

Every rule here is true of any product-development project — which is why GTF, a method for any work, does not say it. What differs between projects — how a PR is merged, what happens after, what proves a task done — is an extension point named in **bold** and answered by the project's [parameters](parameters.md); the [precedence](../../flow-setup/SKILL.md#precedence) says how the two combine.

| # | Loop rule | GTF it applies | What the loop adds |
| --- | --- | --- | --- |
| 1 | **Autonomy** | GTF-T1, GTF-T3, GTF-N6, GTF-U1 | A clear task is worked to its close without the user. Choices in **Human-reserved decisions** are never delegated; each blocks only its task, other work continues. |
| 2 | **Open questions only** | GTF-T3 | A choice the task, the standing decision or a project rule already makes is not open: implement it. An open one runs the **Decision gate** before it becomes a `decision`. |
| 3 | **Standing decision as basis** | GTF-T1, GTF-A2, GTF-E4 | One standing decision per project authorises the loop; it is cited on every write. |
| 4 | **Done is the project's closing evidence** | GTF-E3, GTF-E8, GTF-T4, GTF-T5 | A task closes on its **Closing evidence**, checked against the **Verification target**, with what was observed as `outcome`. A check owed after the merge is GTF-E8's, stated in the task's wait; a failed one returns the task to `active` with what was observed, and work it reveals `blocks` the task (GTF-T4). |
| 5 | **Step order** | GTF-E1, GTF-T2 | First open step, no waiting: merge a done PR (**Merge rule**) → run the **Release procedure** on what merged → work the tasks it unblocks → run the checks that came due → start the next ready task, including while a deploy runs. |
| 6 | **Delivered is not in effect** | GTF-E8, GTF-S5, GTF-N4 | Between merge and closing evidence, every step of the **Release procedure** is a task or a wait in Flow: the loop's steps are tasks that `block` the merged tasks they ship (never the reverse, and never also named in a wait), automatic ones `scheduled` waits, a person's `external` waits. The check itself is the wait GTF-E8 writes once the steps are done. |
| 7 | **Every wait lives in Flow** | GTF-S3, GTF-S5, GTF-N4 | CI, a deploy or a pipeline is a `scheduled` wait; a reviewer is `external`. The PR is an `implements` reference and the next step is in the body. |
| 8 | **One manager role, which implements nothing** | GTF-T6, GTF-E5 | The manager merges, runs the release procedure's loop steps through children, starts and ends child runs; each ready task gets its own child run, which pursues it to its close or its **Child handoff**. Several managers on one project are that one role: they share the run limit, each claims a task on its own run before taking it, and a take that lost a race starts nothing. |
| 9 | **The manager holds no state** | GTF-S4, GTF-S7, GTF-U4 | A delegated task's child is a Flow agent run that `works_on` it; a new manager rebuilds everything from `get-next` and `list-agent-runs`, and "since the last run" is since the previous manager run on the project. |
| 10 | **Parallel; checks win a slot** | GTF-E8, GTF-T6, GTF-U2 | Advance every cleared wait before new work. Under the run limit (`--max-runs`: the project's running children, whichever manager started them), a free slot goes first to a check that came due, then to `get-next`'s candidates with `limit` set to the run limit. |
| 11 | **Runs close as they finish** | GTF-S3, GTF-S7, GTF-S8 | A run whose part is done and written back is ended by its starter, or by itself when nothing started it. A child's part ends at the task's close, or earlier at the **Child handoff**. A manager ends only the children its runtime can read, whichever tick started them; any other running run marks its task taken. |
| 12 | **Bugs and findings** | GTF-T4, GTF-C1, GTF-C2, GTF-C3, GTF-C4, GTF-L3, GTF-A3 | Work the task cannot finish without becomes a task that `blocks` it, with the evidence (`file:line`, request, log). Everything else follows the **Findings rule** — whose default covers a credential with no inbox; search first, add to a match, and tell the user when it is urgent. |
| 13 | **Children implement; the manager holds decisions** | GTF-T3, GTF-T6, GTF-N6, GTF-U3 | A child only implements, and runs the **Local checks** before it pushes: it never asks the user and never waits on a person. On an undelegated choice it writes the `decision` that `blocks` its task (the options, what each worsens, a recommendation), writes the task's state, releases it and ends its turn; a wait only a person can clear is the same. Friction it meets goes in its final message, for the manager to file. No child is ended before the graph holds its state, written by the child or else by the manager. The manager ends that child; the decision reaches the user through the graph, and the task goes to a fresh child once it is answered. |
