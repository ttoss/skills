# Health

`/flow <project id> --health` runs the [Health](https://raw.githubusercontent.com/ttoss/ttoss/main/docs/website/docs/engineering/workflow/routines.md#standard-routines): why it exists is that page's; what it reads and writes is this one's. The run works on no task. It records its run in section 0 with `agent: flow health`, and its only writes are the `decision` tasks of steps 4 and 5. It needs `get-project`, `get-project-metrics`, `get-next`, `list-captures`, `list-tasks`, `get-task`, `upsert-tasks`, `upsert-agent-run` and the delivery's tool.

**Every number is one Flow answers, written as answered**, never a ratio, a goal or a threshold. It is computed by `scripts/health.mjs` in this skill's directory, never by hand, as Flow's [Reading a project's health](https://flow.ttoss.dev/docs/practice/health) reads it. The windows are the 7 days ending now and the 7 before.

**Read the Health's row in the `Routines` parameter first**, in the project's parameters file that its entry section names, and load the delivery's tool before step 1: the row says where the report goes.

1. **The inbox** is the account's, in no project, so a key restricted to one is never given it: `list-captures` with `triaged: false` and `limit: 1`, saved to a file exactly as the tool returned it.
2. **The lines.**
   - **With `FLOW_API_KEY` in the environment**: from the repo's root, `node <this skill's directory>/scripts/check.mjs --root .` first (`ok: false` → by hand, and the final message names the failing check), then `node <this skill's directory>/scripts/health.mjs report --root . --inbox <file>`. It answers `{ alert, lines, mismatches, answers, drain, needs }`. With `--root` it reads the tick's snapshot (section 1 of the tick, the code host through `gh`) for the queue lines and `drain`, and what it could not read is under `needs`. Never print, echo or log the key.
   - **Without it**, by hand:
     1. `node <this skill's directory>/scripts/health.mjs windows <now, ISO 8601>` gives `thisWeek` and `weekBefore`.
     2. For each window, `get-project-metrics` with the project's id, once with `group_by: on`, once plain and once with `tag: [bug]`. Save each answer to its own file exactly as the tool returned it.
     3. `health.mjs flow --this <file> --before <file> --bug-this <file> --bug-before <file>` with the grouped and bug answers, then `health.mjs feeds --this <file> --before <file> --inbox <file>` with the plain ones.
     4. The answers: `list-tasks` with `kind: [decision]` and `status: [completed, cancelled]`, then `get-task` on each closed within four weeks, for its `outcome`.
     5. The queue lines: the tick's snapshot (section 1) and `get-next` with `status: [waiting]` and `assignee: ["any"]`, saved to files, through `health.mjs queues --snapshot <file> --decisions <file>`.

   A non-empty `mismatches` is read again once. `node` or the script missing, or a read failing, leaves those lines out with one line saying why.
3. **The report**, in the project's language. The `alert`, when not `null`, opens it, addressed to the project's `admin` members. Then the lines unchanged, in their order: the flow's health with a line per person and state the person queue waits in, rework after the check and failure demand; then the oldest item in each queue only a person drains and, at its limit, how many changes it proposes to drain; then incubated work and the untriaged inbox; then how many decisions a person answered.
4. **An answer given more than once is a standing rule.** Read the `answers` for the same kind of choice answered the same way twice or more (a test, a threshold, a dependency, a wording, a target). That reading is a judgment and stays here, never in a script. For each such group whose rule the standing decision does not already state, in its body or the document it names on the default branch, and no open task already proposes (`list-tasks` with `query`): write one task of kind `decision`, `waiting` (`external`, `on` the person who answered), tagged `flow-health`. Its body holds the rule as it would be written into the standing decision, each answer it generalises by `url` with the person's words verbatim, and what the rule would let agents stop asking (GTF-E9, GTF-A4). It proposes; the person's `outcome` is the rule, and amending the standing decision is theirs. A single answer, however broad, is never generalised: one answer authorises what it answered (GTF-E9), and the second is what shows it was meant as a rule. Add one line per task written, by `url`.
5. **A full release queue is drained, never only held** ([principle](https://ttoss.dev/docs/engineering/workflow/principles#a-full-queue-is-drained-never-only-held)). When `drain` is not empty and no open task tagged `flow-health-drain` already proposes it (`list-tasks` with `tag`): write one task of kind `decision`, `waiting` (`external`, `on` the project's `admin` members), tagged `flow-health` and `flow-health-drain`. Its body lists each change in `drain` by `url`, with its age, what is left to finish it and who acts, in that order, and asks the person to close each, cut it down to what is worth shipping, or return its task to `incubated`. It weighs what is left to finish, never what was spent, and closes nothing itself: that is the person's. Add one line with its `url`.
6. Deliver the report where the Health's row in `Routines` says. Only a row that names no destination makes it the run's final message, which the runtime delivers to the routine's owner. A delivery that fails or is refused closes the run `failed`, with the reason in its final message beside the report.
7. The `Runtime`'s acts on every run, then close the run.

What the agents spend is the Audit's ([`token-audit`](../../token-audit/SKILL.md) `--routine`), at the end of the week. Never move a task, change a wait, or write anything but the run and the `decision` tasks of steps 4 and 5.
