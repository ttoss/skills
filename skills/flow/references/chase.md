# Chase

`/flow <project id> --chase` runs the [Chase](https://raw.githubusercontent.com/ttoss/ttoss/main/docs/website/docs/engineering/workflow/routines.md#standard-routines): why it exists is that page's; what the digest holds and its shape are this one's. The run works on no task and writes nothing to Flow but its run, recorded in section 0 with `agent: flow chase`; it needs what section 1's snapshot reads, `get-project`, `get-next`, `upsert-agent-run` and the delivery's tool.

**The Chase follows the tick's priorities.** It reads the same snapshot the tick reads (section 1), counts the review queue as the planner does, and lists what only a person can move in the order the tick works. What an agent can move never reaches it: a person's attention goes where the tick is waiting on them.

**With `FLOW_API_KEY` in the environment, the digest is a script.** From the repo's root, run `node <this skill's directory>/scripts/check.mjs --root .` first; `ok: false` → the run uses the steps below by hand and its final message names the failing check. Then `node <this skill's directory>/scripts/chase.mjs --root .`: it reads the parameters (`scripts/params.mjs`: the project, `Review queue`, `Chase lines`, the `Repos`) and the snapshot (`scripts/snapshot.mjs`, the code host through `gh`). Its `digest` is the digest of step 4: translate its words into the project's language, keep its numbers and links, and go to step 5. What it could not read is under `needs`, as the snapshot's. Never print, echo or log the key. The steps below are what the script does, and what a run without a key does by hand.

**Read the Chase's row in the `Routines` parameter first**, in the project's parameters file that its entry section names, and load the delivery's tool before step 1: the row says where the digest goes, and a run that never read it ends with the digest in a final message nobody reads.

1. **The review queue**, as the planner counts it: from section 1's snapshot, each task whose `implements` change is open past draft, or integrated with a wait on a person. Its size against `Review queue` (default 20).
2. **What only a person can move**: of those, each task with a wait `on` a person or a team. A task in the queue that waits on nobody is at its gates or with the agents, and is left out. Ordered as the tick orders work (process rule 3): a `very_high` task, then a `high` bug; then an open change before integrated work waiting to be seen; then Flow's ranking, priority then how many tasks it frees (`unblocks`); then the earliest date its wait gives. Show `Chase lines` of them (default 20) and how many there are.
3. **Decisions the team owes**, only while the queue is within its limit (its size at most `Review queue`): `get-next` with `kind: [decision]`, `status: [waiting]` and `assignee: ["any"]`, in Flow's ranking; show half as many as step 2 (default 10) and how many there are. Over the limit the tick starts no new work, and a decision holds only the work it blocks, so the digest leaves them out.
4. **Write the digest** in the project's language: a title line with the date; one line with the queue's size and limit, saying whether the tick starts new work; then **Only a person can move these**, and, within the limit, **Decisions the team owes**. Each line is `[title](url) — <who acts> — <what they do, from the wait's reason>`. Who acts is whom the wait is `on`: a person by their email in Flow (`get-project`), a team by its members' emails, or, for a wait on nobody, the project's `admin` members. Never an `@handle`: a delivery sent as text does not turn it into a mention. An empty list says `none`.
5. Deliver it where the Chase's row in `Routines` says, such as a channel; only a row that names no destination makes it the run's final message, which the runtime delivers to the routine's owner. A delivery that fails or is refused closes the run `failed`, with the reason in its final message beside the digest.
6. The `Runtime`'s acts on every run, then close the run. The final message is the digest, or one line naming where it went and how many lines it holds.

The flow's health, each state's arrivals against departures and the line per person, is the Audit's (`token-audit`), weekly.

Never move a task, change a wait or its `until`, or send anything but the one digest.
