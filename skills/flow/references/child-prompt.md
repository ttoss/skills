# Child prompt

Fill the `<…>` slots, each parameter's value from the project's [parameters](parameters.md) or the default there, pointers kept as pointers, and start the child with it. Add nothing else: a limit or branch the template and the parameters do not state overrides what the project says, and the child follows the prompt. It is self-contained, since the child's repo may not have this skill, and short on purpose, since the child re-reads it on every turn. `<child address>` is "your session's URL" when the runtime gives each child one, else the `<tick address>?task=<task id>` the tick computed.

```text
Repos: <each repo the task touches, with the path of this child's own copy, and for a copy not yet made the clone command at that path>. Work in no other checkout, and touch no other path in a space you share.
Task <task_id> (<task url>), Flow project <proj_id>. First record your run: `upsert-agent-run` with `url` <child address>, `works_on: [<task_id>]`, `parent: <tick run id>`, `agent: flow child`, `hold_minutes: <Stale after, in minutes>` and your model. If the task comes back `contended`, another run holds it: stop. Stop too when a write answers `contended` or `untaken`. Don't close your run; the tick does. Leave `basis` off your Flow writes, which inherit the standing decision through your `parent`; give one only for another cause: a URL, or a person's words as `said`. Write as few words as carry the meaning; full sentences only for what a person reads later.
1. `get-task`: the brief, whose purpose is what you answer every choice on the way against, and on a later round the log or findings that sent it back. If its acceptance already holds (an integrated change, the code, the effect): add the `implements` reference and `after_integration`, stop.
2. Before proposing: `get-task` again. A status or `implements` reference that moved since step 1 without you means another session worked the task: drop your change, stop. Then <Before proposing>. A required check that cannot finish within your run: run it scoped to what you changed (those modules' tests, typecheck, lint), and name in the description each check left to CI and why. A local failure the default branch shows too says nothing about your change. Propose the change ready (not draft) only when nothing is left to push, or push to the open one on a later round. Its description carries this task's URL and every other task it settles, each with why.
3. Handoff: the change as an `implements` reference; `after_integration`, what integrating leaves: `{ leaves: close }` when <Closing evidence> holds once it integrates, `{ leaves: release }` when a release step puts it in effect, or `{ leaves: check, check: { observe, where, visible_at } }` with what to observe and the result that means it worked, where, and when it can first be seen; the task `waiting` (`external`) on its gates: <Review> and the checks. In the change's description, the assumptions you made and the choices you answered yourself, each as `Q`, `A`, the <Decisions> test that answered it and what you checked. Then stop watching the change and end your turn; the tick writes everything after the verdict.
4. A choice nobody has made (one in <Decisions>, or still open after its test) or an act only a person can do: move the task to `waiting` (`external`, `on` the person), the reason holding the trade: the question, each option and what it worsens, the premise still open, your recommendation and the pain that would activate it. Stop.
5. Work you notice outside the task: <Intake>. Don't widen the change.
6. Friction with a skill, GTF or a Flow tool: file it with `flow-friction` (search first), then continue.
```

A check child, on the check model, gets the same first line, naming every task its checks cover in `works_on`, and instead:

```text
For each task, run the check in its wait against <Closing evidence>, and every step it names after the result. Before moving a task outside `works_on`, add it with `upsert-agent-run` (`works_on` only adds); if it comes back `contended`, leave it. Close the task with what you observed as `outcome`, or move it to `active` with the observation when the effect is not there. When what you observe is harm the change caused, a regression, pull the change first by the reversal path its description records, add the revert as a reference citing what you observed, and say so in the body, so the fix starts from a product that works; a change that records no path waits on the person (`external`, `on` them), naming the harm, since a reversal nobody designed is not yours to invent. When it cannot be seen yet, move the wait's `until` to when it can, from something you can point to. When you cannot run the check, such as a credential or access you lack, move the task to `waiting` (`external`, `on` the person) naming what is missing, never to `active`. Whenever you move the check's date, write it as `after_integration.check.visible_at` too, so the handoff never names a date the check already failed on.
```

A review child, on the review model, gets the same first line with the change's task in `works_on`, and instead:

```text
Review <change url> as someone who did not write it. Pass or fail each item with its evidence (`file:line`): the diff does what the task's acceptance asks and nothing its out of scope excludes; what changed has no bug; the description carries the task's URL, the tasks it settles and every change to the change's own gates (a test removed or skipped, a threshold lowered, CI configuration or required checks altered), and the task's body says what integrating leaves, with its check; and the checklist <Review> names, if any. First set the `flow/review` commit status `pending` on the head you review (`gh api repos/<owner>/<repo>/statuses/<head sha> -f state=pending -f context=flow/review`), so no second reviewer starts. End with one comment on the change: `CLEAN`, or `FINDINGS` with each failed item, ending in `<!-- flow-verdict sha=<head sha> result=CLEAN|FINDINGS -->`. Then set the same status `success` for CLEAN or `failure` for FINDINGS, its `target_url` that comment. The status is the verdict the tick and the code host read; the marker counts only when the status cannot be set. A push after it makes the verdict stale. Write nothing on the task: the tick does after the verdict. Never push to the change, approve it or integrate it.
```

A repair child gets the same prompt, and before step 1:

```text
The default branch of <repo> is red at <sha>: <the failing check>. Fix it by code, keeping what every change that landed meant to do. Revert a change only when no fix by code is possible, and say in the task why; a revert makes the reverted task's successor, which `supersedes` it, never a reopen.
```
